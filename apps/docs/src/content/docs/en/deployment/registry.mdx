title: Deployment and package registry
description: Prepare Karsa bindings, secrets, migrations, and private module registry access for a deploy.
---

## Local first

Use Wrangler's local D1 and R2 emulators while developing:

```sh
bunx karsa db sync
bunx wrangler d1 migrations apply DB --local
bunx karsa db seed
bun run build
```

Keep `wrangler.jsonc` bindings named `DB` and `MEDIA`. Local `.dev.vars` is gitignored; put `BETTER_AUTH_SECRET` and the scaffold-generated `KARSA_SETUP_TOKEN` there. Use Wrangler secrets for deployed environments:

```sh
bunx wrangler secret put BETTER_AUTH_SECRET
bunx wrangler secret put KARSA_SETUP_TOKEN
```

If the booking module is installed, configure a separate Turnstile widget for this application. Set `TURNSTILE_SITE_KEY` and the comma-separated production `TURNSTILE_HOSTNAMES` as deployment variables, then save `TURNSTILE_SECRET` with Wrangler. Do not use the scaffold's local dummy keys in production, do not include `localhost` in production hostnames, and never print the secret in logs or reports.

## Documentation canonical URL

Set `DOCS_SITE_URL` to the public documentation origin when building the docs deployment. Local builds intentionally default to `http://localhost:4321`, while the deployment value drives canonical URLs and the generated sitemap without hard-coding an unconfirmed production domain.

```sh
DOCS_SITE_URL=https://docs.example.com bun run --cwd apps/docs build
```

## Registry access

Public packages resolve from npm. If a selected module is hosted in a private registry, configure the `@karsa` scope and credentials in a user or CI `.npmrc`; never commit a token. Verify the package graph before running the CLI so `karsa add` can resolve the module and its dependencies.

## Deploy checklist

1. Create the real D1 database and R2 bucket, then update deployment bindings.
2. Apply the append-only migration plan to the remote database, including the orders upload/idempotency, booking fingerprint/quota, and catalog inventory-allocation migrations.
3. Add deployment secrets and confirm the origin/allowed-host configuration. Complete first-run setup with the bootstrap token.
4. If serving legacy SVG media, convert and re-upload it as an allowed raster type; the public media route now returns `415` for unsafe MIME metadata.
5. Build with the same registry and lockfile used by CI.
6. Smoke-test public routes, auth mode, guarded routes, media downloads, booking Turnstile, checkout idempotency, and one module-owned flow.

Do not seed remote data with the local-only `karsa db seed` path. Use a reviewed migration or explicit operational import for production data, and record the command output as evidence.
